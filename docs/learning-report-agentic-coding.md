## 核心结论

> Agentic Coding 提效的关键在于**优化与 AI 的协作方式**，而非寄望于无限上下文窗口。
> 核心策略：**短对话、精简上下文**，拆解任务为专注的子对话，借助"复利工程"沉淀经验。

## 上篇：LLM 本质 & Agent 实现原理

### 一、LLM 的三个本质特征

| 特征 | 含义 | 工程启示 |
|------|------|----------|
| **推理=生成本身** | 没有独立于输出的思考，只能边想边说 | 用 CoT（一步步思考）给模型更多"思考空间" |
| **上下文=全部记忆** | 没有独立记忆存储，窗口外的东西不存在 | 关键信息必须显式放入上下文 |
| **生成具有概率性** | 同一个输入可能不同输出 | 不能期待每次都完美，需要验证循环 |

### 二、Coding Agent 的五大问题

| # | 问题 | 表现 |
|---|------|------|
| 1 | **局部最优** | 边写边想，缺全局规划；多文件重构时接口不一致 |
| 2 | **偏差滚雪球** | 早期误读→后续在错误世界观里自洽→越写越像另一个项目 |
| 3 | **流式输出不可回改** | 擅长写新文件，不擅长精确局部编辑；倾向重写→diff 过大 |
| 4 | **约束满足弱** | 边界条件/并发/错误处理常出错；缺 AST 辅助 |
| 5 | **单线程思考** | 早早押注一个方向，缺少并行方案对比 |

### 三、Attention 机制

- Attention 像"动态聚光灯"，每次生成 token 时扫视上下文分配权重
- **稀疏性**：注意力集中在少数关键位置
- **平方复杂度**：计算量随上下文长度平方增长 → 上下文有物理上限

### 四、上下文长度——最关键约束

- **物理上限**：主流模型 128K~200K tokens（O(n²) 复杂度导致）
- **有效上下文 < 标称上下文**：200K 模型在 80K~100K 后性能退化
- **性能退化曲线**：上下文越长 → 推理准确性/指令遵循/代码质量都下降

### 五、强化学习（RL）

- 预训练只能"说"，RL 让模型学会"做"
- 核心循环：**尝试 → 反馈 → 调整**
- 适合 Agent 任务（路径多样、结果导向、需要探索）
- 关键启示：提供清晰成功标准、允许试错、Agent 训练中学会了通过尝试解决问题

### 六、Coding Agent 实现原理

**API Messages 结构**：system / user / assistant 三种 role

**Tool Calling**：定义工具 schema → 模型生成结构化调用 → 结果回传

**Prompt Caching**：缓存前缀匹配，稳定内容（system + tools）放前面，动态内容（对话历史）放后面

**Agent Loop**：
```
调用模型 → 检查是否需要工具 → 执行工具 → 结果返回模型 → 重复 → 最终响应
```
停止原因：`end_turn`（正常结束）/ `tool_use`（继续行动）/ `max_tokens`（截断错误）

## 下篇：实操最佳实践

### 一、短对话优于长对话（最重要实践）

- 长对话表现像"喝醉"：犯错、重复、偏离目标
- 长对话成本指数级增长（每次发送整段上下文）
- 长对话更容易错过缓存窗口 → 费用飙升
- **结论：一个对话只做一件事**

### 二、以对话为单位组织工作

```
功能：用户登录后的会话管理
 ├── [对话1] 调研现有代码结构
 ├── [对话2] 实现基础功能
 ├── [对话3] 添加错误处理
 ├── [对话4] 编写测试
 ├── [对话5] 代码审查
 └── [对话6] 清理重构
```

**对话间上下文传递**：
- 引用之前对话结论 → 新对话开头说明
- 利用 Git 状态 → `git diff`
- 使用项目文档 → `AGENTS.md`
- `#mention` 相关文件

### 三、项目配置文件（AGENTS.md）

- **自动注入每个对话** = 最高杠杆点
- 回答三个问题：**WHAT**（技术栈/结构）、**WHY**（设计决策背景）、**HOW**（构建/测试/验证）
- **少即是多**：控制在 300 行以内
- **渐进式披露**：配置文件指向详细文档，Agent 按需读取
- **偏好指针而非副本**：用 file:line 引用，避免过时
- **不要让 Agent 做 Linter 的工作**：交给 Prettier/ESLint

### 四、200K Token 足够了

- 关键不在窗口大小，在如何使用
- 每个对话 80K-100K，但可以开 10+ 个对话 → 总量远超单窗口
- 实践：超过 80K-100K 开新对话；Agent "醉酒"时立即新对话

### 五、Compounding Engineering（复利工程）

> 你不只是在解决问题，而是在教育系统

| 实践 | 做法 |
|------|------|
| 经验沉淀 | bug 修复后写入 AGENTS.md / Lint 规则 / 测试 |
| Bug 产生长期价值 | 问自己：Lint 可预防？教训可记录？测试可防回归？ |
| 审查提取模式 | 审查意见 → 编码规范 → Agent 自动应用 |
| 工作流复用 | 沉淀有效工作模式，下次说"按某工作流做" |

**复利效应**：第一周几条规范 → 第一个月完整知识库 → 三个月后 Agent 自动应用你从未明说的模式

### 六、对人难的事，对 AI 也难

**双重价值投资**：所有提升人类开发者体验的工作，对 AI 同样有价值

| 投资方向 | 具体做法 |
|----------|----------|
| 更好文档 | 架构决策记录（ADR）、API 示例、已知陷阱 |
| 清晰代码结构 | 清晰命名、单一职责、显式依赖 |
| 快速反馈循环 | 秒级单测、快速增量构建、本地可运行环境 |
| 为 AI 优化测试 | 可局部运行测试（`npm test -- --grep "xxx"`） |
| 快速健康检查 | `scripts/quick-check.sh`（typecheck + lint + test） |
| 文档放代码旁边 | 模块级 README.md |

## 对 Rupoo 项目的直接启示

1. **项目已有 AGENTS.md / .trae/rules** → 这是正确的方向，应持续维护精简
2. **短对话原则**：UI 重构和 Agent 逻辑应拆分为独立对话
3. **复利工程**：每次 bug 修复/代码审查后，更新项目配置文件
4. **快速反馈**：`cargo check` / `pnpm typecheck` 应作为 Agent 常用验证工具
5. **上下文管理**：不要让 Agent 一次性加载整个项目，用 `#mention` 精确引用文件
